# Переезд UmaiSense в Freedom Cloud (Казахстан)

Цель: все персональные и медицинские данные (база, документы, фото, бэкапы) хранятся на серверах в РК,
прод переживает падение любого одного сервера, а обновления выходят без простоя.

> Я не юрист. Текст согласия, политику конфиденциальности (страница `/privacy`, черновик в
> `umiasense-front-main/src/pages/legal/PrivacyPage.tsx`) и регламент инцидентов должен проверить юрист в РК.

---

## 1. Почему переезжаем

| Сейчас | Проблема | После переезда |
|---|---|---|
| База — MongoDB Atlas (за рубежом) | Закон РК № 94-V, ст. 12: база с персональными данными должна находиться в РК | MongoDB на серверах Freedom Cloud |
| Документы и фото — Cloudinary (за рубежом), **по открытой ссылке** | Медицинские документы доступны любому, у кого есть ссылка | Закрытое хранилище в РК, ссылка на 5 минут после проверки прав |
| Документы отправлялись в OpenAI | Трансграничная передача медицинских данных | ИИ-разбор документов отключён, рекомендации — по обезличенным данным |
| API на Vercel (за рубежом) | Персональные данные обрабатываются и пишутся в логи вне РК | API на серверах в РК |

## 2. Что заказать у Freedom Cloud

По открытым данным Freedom Cloud (fcd.kz) предлагает облачные серверы и колокацию в ЦОД уровня Tier III
(ISO 27001, SLA 99,982 %). Управляемых MongoDB и S3 в публичном каталоге я не нашёл, поэтому схема ниже
построена на обычных виртуальных серверах. **Перед заказом уточните у менеджера:**

1. Есть ли **управляемая MongoDB** и/или **S3-хранилище** в РК? Если есть — узлы `data1–3` можно не поднимать,
   а в `.env` указать их адреса (код работает с любым S3-совместимым хранилищем).
2. Есть ли **балансировщик нагрузки** или **плавающий (резервный) IP**? Если да — `lb1` можно заменить им
   и убрать единственную точку отказа.
3. Можно ли разместить серверы **в разных ЦОД** (например, Караганда + другой город)? Узлы данных лучше
   разнести — тогда авария целого ЦОД не остановит сервис.
4. **Частная сеть** между серверами, **файрвол** (security groups), **снимки дисков**.
   **Шифрование дисков обязательно** для узлов данных и бэкапов: Garage не шифрует файлы сам. Если у Freedom Cloud
   нет шифрования дисков — используйте LUKS (dm-crypt) на дисках `/srv/mongo` и `/srv/garage`.
5. Документы для проверки соответствия: подтверждение размещения в РК, ISO 27001, договор с пунктами о
   конфиденциальности и обработке персональных данных.

### Серверы (на 10–20 тыс. пользователей, с запасом)

| Сервер | Кол-во | vCPU | RAM | Диск | Назначение |
|---|---|---|---|---|---|
| `lb1` | 1 | 2 | 2 ГБ | 20 ГБ | nginx: HTTPS, фронтенд, балансировка, вход в S3 |
| `app1`, `app2` | 2 | 2 | 4 ГБ | 40 ГБ | API (Docker) |
| `data1`, `data2`, `data3` | 3 | 4 | 8 ГБ | 100 ГБ SSD (MongoDB) + 500 ГБ (файлы) | MongoDB + Garage (S3) |
| Хранилище бэкапов | — | — | — | ~1 ТБ | **в другом ЦОД** (другой город Freedom Cloud или S3 другого провайдера в РК) |

Оценка объёма: база — единицы ГБ; файлы — 20 тыс. детей × ~10 документов × ~1,5 МБ ≈ 300 ГБ.
Garage хранит 3 копии (по одной на узле), поэтому каждому узлу данных нужен диск на весь объём файлов.

## 3. Схема

```
                     Интернет (HTTPS)
                           │
                  ┌────────▼────────┐   app.umaisense.kz  — сайт + /api + /media
                  │   lb1 (nginx)   │   s3.umaisense.kz   — загрузка/скачивание документов
                  └──┬──────────┬───┘
         /api        │          │   S3 (3900) / картинки (3902)
        ┌────────────┘          └───────────────┐
  ┌─────▼─────┐  ┌─────────────┐                │
  │   app1    │  │    app2     │  API в Docker   │
  └─────┬─────┘  └──────┬──────┘                 │
        └──── частная сеть 10.10.0.0/24 ─────────┤
  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐
  │ data1       │ │ data2       │ │ data3       │   MongoDB: набор реплик rs0 (1 PRIMARY + 2 SECONDARY)
  │ Mongo+Garage│ │ Mongo+Garage│ │ Mongo+Garage│   Garage: 3 копии каждого файла
  └─────────────┘ └─────────────┘ └──────┬──────┘
                                          │ ежедневно, зашифровано
                                ┌─────────▼─────────┐
                                │ Бэкапы в другом ЦОД│
                                └────────────────────┘
```

Что выдерживает схема:

- падение `app1` или `app2` — nginx переводит трафик на второй, пользователи не замечают;
- падение одного узла данных — MongoDB за ~10 с выбирает новый PRIMARY, Garage продолжает читать и писать;
- обновление кода — серверы приложения обновляются по одному (`deploy/deploy-app.sh`);
- потеря всех узлов данных — восстановление из бэкапа в другом ЦОД (данные за последние сутки).

Слабое место — `lb1`. Если Freedom Cloud даёт балансировщик или плавающий IP, используйте их.
Если нет — держите готовый снимок `lb1`: он без данных и пересоздаётся за минуты.

Адреса в конфигах (`10.10.0.x`, `umaisense.kz`) — примеры, замените на свои.

## 4. Пошаговая установка

### 4.1. Сеть и файрвол

- Все серверы — в одной частной сети. Публичный IP — только у `lb1`.
- `lb1`: открыть 80 и 443 из интернета.
- `app1/2`: 5000 — только с `lb1`; 22 — только с вашего IP или VPN.
- `data1–3`: 27017 и 3901 — только из частной сети; 3900 и 3902 — только с `lb1`; 3903 — закрыт.
- На всех: автоматические обновления безопасности (`unattended-upgrades`), вход по SSH только по ключу.

### 4.2. Узлы данных (data1, data2, data3)

```bash
# На каждом узле: Docker, диски /srv/mongo и /srv/garage
git clone <репозиторий> /opt/umaisense
mkdir -p /opt/umaisense-data /srv/mongo /srv/garage/meta /srv/garage/data

# Общий ключ MongoDB — создать один раз и скопировать на все 3 узла
openssl rand -base64 756 > /opt/umaisense-data/mongo-keyfile
chmod 400 /opt/umaisense-data/mongo-keyfile && chown 999:999 /opt/umaisense-data/mongo-keyfile

# Конфиг Garage: секреты одинаковые на всех узлах, rpc_public_addr — адрес этого узла
cp /opt/umaisense/deploy/data/garage.toml /opt/umaisense-data/garage.toml && nano /opt/umaisense-data/garage.toml

# Переменные для docker compose (файл рядом с docker-compose.yml, права 600)
cat > /opt/umaisense/deploy/data/.env <<'ENV'
PRIVATE_IP=10.10.0.11
MONGO_ROOT_USER=root
MONGO_ROOT_PASSWORD=<сгенерировать: openssl rand -base64 32>
ENV
chmod 600 /opt/umaisense/deploy/data/.env
docker compose -f /opt/umaisense/deploy/data/docker-compose.yml up -d
```

Затем, один раз на `data1`:

1. Набор реплик MongoDB:
   `docker compose -f deploy/data/docker-compose.yml exec mongo mongosh -u root -p --authenticationDatabase admin /init/init-replica-set.js`.
   Затем на PRIMARY создайте пользователей `umaisense` (только своя база) и `backup` — команды в конце того же файла.
2. Кластер Garage, ключ, бакеты и CORS — по шагам из `deploy/data/setup-garage.sh`.

Проверка: `rs.status()` показывает 1 PRIMARY и 2 SECONDARY; `garage status` — 3 узла.

### 4.3. Серверы приложения (app1, app2)

```bash
git clone <репозиторий> /opt/umaisense
cp /opt/umaisense/umaisense-back-main/.env.example /opt/umaisense/.env
nano /opt/umaisense/.env      # заполнить все значения; одинаково на app1 и app2
chmod 600 /opt/umaisense/.env
echo "PRIVATE_IP=10.10.0.21" > /opt/umaisense/deploy/app/.env   # на app2 — 10.10.0.22
docker compose -f /opt/umaisense/deploy/app/docker-compose.yml up -d --build
curl -fsS http://127.0.0.1:5000/api/health/ready     # {"status":"ok","db":"ok"}
```

Обязательные переменные (без них сервер в продакшене не стартует или документы не загружаются):

- `JWT_SECRET` — 32+ символа, `openssl rand -base64 48` (без него сервер в продакшене не работает);
- `MONGO_URI`, `CLIENT_URL`;
- `S3_*` — данные ключа Garage;
- `ALLOW_VERCEL_PREVIEWS=false` — после переезда.

### 4.4. Балансировщик (lb1)

DNS `app.umaisense.kz` и `s3.umaisense.kz` должны уже указывать на `lb1`.

```bash
apt install nginx certbot
mkdir -p /var/www/certbot /var/www/umaisense

# 1) Временный конфиг только с портом 80 — чтобы выпустить сертификаты
cp /opt/umaisense/deploy/lb/umaisense-http-only.conf /etc/nginx/conf.d/umaisense.conf
nginx -t && systemctl reload nginx
certbot certonly --webroot -w /var/www/certbot -d app.umaisense.kz
certbot certonly --webroot -w /var/www/certbot -d s3.umaisense.kz

# 2) Полный конфиг
cp /opt/umaisense/deploy/lb/umaisense.conf /etc/nginx/conf.d/umaisense.conf
cp /opt/umaisense/deploy/lb/umaisense-proxy.conf /etc/nginx/snippets/
nginx -t && systemctl reload nginx
```

Продление сертификатов работает автоматически через тот же каталог `/var/www/certbot`.
Журнал запросов nginx содержит IP пользователей. Настройте его хранение не дольше 14 дней
(`/etc/logrotate.d/nginx`: `rotate 14`, `daily`).

Фронтенд собирается и копируется на `lb1`:

```bash
cd umiasense-front-main && npm ci && npm run build      # VITE_API_URL не задавать: API на том же домене (/api)
rsync -a --delete dist/ deploy@lb1:/var/www/umaisense/
```

### 4.5. Перенос данных (окно обслуживания ~30 минут, лучше ночью)

1. **Заранее** развернуть всё по шагам 4.1–4.4 и проверить на тестовых данных.
2. Предупредить пользователей о технических работах.
3. Остановить запись в старую систему: в Vercel удалить `MONGO_URI` и передеплоить
   (API будет отвечать 503, ничего не запишется).
4. Перенести базу:
   `ATLAS_URI=… NEW_URI=… SRC_DB=<имя базы в Atlas> ./deploy/migrate-from-atlas.sh` — скрипт сверит количество записей.
   **После переноса перезапустите API на app1 и app2**: при переносе индексы пересоздаются, новые
   (уникальные, TTL) создаются заново только при запуске приложения.
5. Перенести файлы из Cloudinary (на `app1`):
   ```bash
   docker compose -f deploy/app/docker-compose.yml run --rm api node dist/scripts/migrate-files-to-s3.js --dry-run
   docker compose -f deploy/app/docker-compose.yml run --rm api node dist/scripts/migrate-files-to-s3.js
   ```
   Медицинские документы переедут в закрытый бакет, публичные ссылки на них в базе исчезнут.
6. Переключить DNS `app.umaisense.kz` на `lb1`. Проверить вход, расписание, загрузку и открытие PDF.
7. **После проверки** удалить данные из старых мест:
   - кластер Atlas (сначала сделайте свежий бэкап в РК);
   - файлы в Cloudinary;
   - переменные окружения на Vercel.

## 5. Бэкапы

- `deploy/backup/backup.sh` — каждую ночь:
  - копия MongoDB снимается с SECONDARY и шифруется (`BACKUP_ENCRYPTION_KEY`);
  - файлы синхронизируются в хранилище **в другом ЦОД в РК**;
  - всё хранится 30 дней.
- Ключ шифрования бэкапов храните отдельно от серверов (например, в менеджере паролей у двух человек).
  Без него бэкап не расшифровать.
- **Раз в месяц** проверяйте восстановление по `deploy/backup/restore-check.md`.
- Дополнительно: ежедневные снимки дисков `data1–3` средствами Freedom Cloud.

## 6. Мониторинг

Минимум, который можно поставить за час:

- **Uptime Kuma** на отдельной маленькой ВМ или на `lb1`:
  - проверять `https://app.umaisense.kz/api/health/ready` каждые 30 с;
  - проверять срок действия SSL-сертификата;
  - уведомления — в Telegram.
- Алерты по ресурсам:
  - заполнение дисков `data1–3` больше 75 %;
  - CPU больше 85 % дольше 10 минут.
- Логи — `docker logs`, ротация уже настроена. Приложение не пишет в логи содержимое запросов;
  IP-адреса есть в журнале nginx на `lb1` (14 дней) и в журнале доступа к данным (`auditlogs`, 3 года).
- Лимиты запросов в приложении считаются на каждом сервере отдельно. С двумя серверами фактический лимит
  примерно вдвое выше указанного в `.env`; строгие лимиты на вход и коды стоят ещё и в nginx.

## 7. Если что-то случилось (инцидент с персональными данными)

Действующая редакция Закона № 94-V требует уведомлять уполномоченный орган об утечке или неправомерном
доступе к персональным данным в короткий срок. По обзорам изменений 2026 года — **в течение одного рабочего дня**;
точную статью и порядок уведомления сверьте с юристом. Заранее:

1. Назначьте ответственного за персональные данные и его заместителя.
2. Порядок действий:
   1. Ограничить доступ: сменить `JWT_SECRET` — это разлогинит всех. Сменить ключи S3 и пароли MongoDB.
   2. Выяснить по журналу доступа, чьи данные затронуты: коллекция `auditlogs` и раздел «Журнал доступа» в админке.
   3. Уведомить уполномоченный орган.
   4. Записать хронологию.
3. Раз в полгода проводите учебную проверку этого порядка.

## 9. Что изменилось в коде

**Безопасность (найдено при подготовке, исправлено):**

- Регистрация не проверяла, что email подтверждён кодом, и принимала роль `admin`. Любой мог создать себе
  аккаунт администратора и увидеть ИИН и медицинские данные всех детей.
  Теперь после ввода кода выдаётся одноразовый токен, без него регистрацию не завершить; роль — только
  родитель или тренер.
- Сброс пароля можно было обойти запросом вида `{"code": {"$ne": ""}}` (NoSQL-инъекция) — в том числе
  для администратора. Теперь все поля приводятся к строкам, тела с `$`-ключами отклоняются, у кода 5 попыток.
- `JWT_SECRET` по умолчанию был `secret` — подделать токен администратора мог любой.
  Теперь без надёжного секрета сервер в продакшене не запускается.
- Минимальная длина пароля — 8 символов.
- Лимиты запросов работают по реальному IP за балансировщиком (`TRUST_PROXY`).

**Документы:**

- Поддерживаются PDF, Word (DOC, DOCX) и фото (JPG, PNG, HEIC) до 20 МБ.
- Тип файла проверяется по содержимому, а не по расширению.
- Загрузка идёт напрямую в закрытый S3 в РК, открытие — по одноразовой ссылке на 5 минут.
- ИИ-разбор документов отключён. Старые разъяснения остались у старых документов.

**Персональные данные:**

- Согласия при регистрации и при добавлении ребёнка хранятся в коллекции `consents`.
- Журнал доступа: кто открывал профиль и документы. Его видят родитель (вкладка «Журнал доступа») и администратор.
- ИИ-рекомендации получают данные без имени, фамилии и ИИН.

**Надёжность:**

- `index.ts` и Vercel используют один `createApp`.
- Сервер корректно останавливается при обновлении.
- Проверки `/api/health/live` и `/api/health/ready` (вторая проверяет связь с базой).
- MongoDB: набор реплик, запись с подтверждением большинства (`w: majority`).
- Заголовки безопасности (helmet), общий лимит запросов, единый JSON-обработчик ошибок.
- Dockerfile, конфиги nginx, Garage и MongoDB, скрипты деплоя без простоя, бэкапа и переноса.
